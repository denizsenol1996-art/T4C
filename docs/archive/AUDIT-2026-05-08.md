## 0. Samenvatting

Het platform draait stabiel maar de codebase bevat een groeiend aantal scheuren:

- **2 actieve runtime-fouten** (1 onhandled rejection bij dagelijkse cleanup, 1 endpoint dat consequent 404 geeft)
- **1 structureel logica-bug** in `server.js` waardoor de dagelijkse scrapers binnen een email-poller-interval zijn gewikkeld en elke minuut "Scheduled" loggen
- **Schema mismatch** tussen oude `/api/taxatie/feedback` endpoint en de werkelijke `dealer_feedback` tabel — INSERTs falen sinds 449 entries via nieuwe endpoint
- **Vrijwel alle GPT-leerregels (`pricing_lessons`, 159 rijen) worden nooit gelezen** — dood eindstation
- **CLAUDE.md vs werkelijkheid** wijken op meerdere punten af (DB-driver, actieve users, JWT-secret-locatie, server-versie)
- **66 `.bak`-bestanden** door de codebase, **1.2 GB** historische DB-backups, 5 oude DB-snapshots in `data/`
- **3 ongebruikte lib-modules** (`formula-fallback.js`, `smart-sold-rdw.js`, `stealth.js`)
- **15+ DB-tabellen leeg of nooit gelezen** (zie 5.2)

Niets is acuut breekbaar. Alle items zijn opruim/refactor werk.

## 1. Runtime fouten (productie nu)

### 1.1 `dv-webhook.js:792` — `ReferenceError: scheduleSaveFn is not defined`

```
[2026-05-08T06:00:02.150Z] [WARN] Unhandled Rejection: scheduleSaveFn is not defined
    at /opt/t4c/backend/dv-webhook.js:792:5
```

Triggert elke ochtend om 06:00 wanneer `scheduleDVCleanup()` (regel 798-808) de cleanup-route aanroept. De callsite gebruikt `scheduleSaveFn()` maar de destructuring in `setupDVWebhookRoutes` (regel 529) bindt het als `scheduleSave`. Op regel 603 wordt het correct als `scheduleSave` aangeroepen. Regel 792 is een refactor-restant.

**Fix:** `scheduleSaveFn()` → `scheduleSave && scheduleSave()` (consistent met regel 603).

### 1.2 `/api/search-history` — GET 404, POST bestaat

- Frontend (`sites/cardatax/admin/index.html:613,849,870`) doet `GET /api/search-history?limit=N`
- Backend (`backend/routes/misc.js:293`) heeft alleen `POST /api/search-history`
- Genereert continu 404's (zichtbaar in `errors.log`, tientallen per minuut wanneer admin open staat)
- Frontend heeft een fallback message: "Geen search_history endpoint" — dus weet ervan, maar 404-storm blijft

**Fix:** GET handler toevoegen, of frontend-fetch verwijderen. Tabel `search_history` zelf werkt wel.

### 1.3 `server.js:226-330` — Daily scrapers gewikkeld in email-poller-interval

```javascript
setInterval(() => { try { processEmailQueue() } catch(e) {}

// Daily scrapers logica (~100 regels) hierbinnen ingenest
const runDailyScrapers = async () => { ... }
setTimeout(() => { runDailyScrapers(); setInterval(runDailyScrapers, 24h) }, msUntil3AM())
console.log('[DAILY] Scrapers scheduled for ~3:00 AM')

}, 60000)
```

`runDailyScrapers` wordt elke minuut opnieuw gedefinieerd, en er wordt elke minuut een nieuwe `setTimeout` voor 03:00 + nieuwe `setInterval`(24h) gepland. Effect:

- Logbestand spamt elk 60s `[DAILY] Scrapers scheduled for ~3:00 AM` (zichtbaar in `t4c-server-out.log`)
- Op den duur stapelen `setTimeout`/`setInterval` callbacks zich op (na 24u: 1440 dubbele setIntervals → scrapers draaien meerdere keren per dag, oplopend)
- Verklaart de geheugenbalon en `pm2 ↺ 3` (3 restarts) — past in eerder waargenomen 4G memory-pmconfig in commit `19b9a3d`

**Fix:** sluitende `}, 60000)` voor email-queue verplaatsen vóór de daily-scraper definitie. Het is missende code-haakjes-structuur.

## 2. Code kwaliteit fouten

### 2.1 JWT-secret op twee plekken hardcoded

- `lib/auth.js:3` — fallback hardcoded
- `db.js:737-742` — random gegenereerd in `settings.jwt_secret` bij eerste boot
- `server.js:200-201` — leest uit DB, zet via `auth.setSecret(JWT_SECRET)`

Werkt, maar de hardcoded fallback in `lib/auth.js` is een security-smell (CLAUDE.md noemt dit ook expliciet). Bovendien zegt CLAUDE.md "JWT_SECRET hardcoded in `lib/auth.js`" terwijl de echte secret nu uit de DB komt — documentatie loopt achter.

`backend/.env` heeft óók een `JWT_SECRET=...` regel, maar die wordt nergens gelezen (server.js gebruikt `getJwtSecret()` uit `db.js` die uit settings-tabel leest).

### 2.2 `lib/auth.js` exporteert geen `verifyToken`

`routes/valuation.js:20` doet `const { verifyToken } = require("../lib/auth")` — die functie is niet gedefinieerd noch geëxporteerd. `verifyToken(t)` retourneert dus `undefined` → `_userId = u?.uid || null` valt altijd terug op `null`. Bedoeld als optionele auth — werkt niet zoals bedoeld, maar faalt stil.

### 2.3 `users.json` is dood

```json
{ "secret": "deprecated_use_lib_auth_js", "users": [] }
```

Bestand wordt bijgehouden via `users.json.bak-20260507-2307` en `bak-2308`, suggereert dat scripts er nog naar refereren. CLAUDE.md zegt het is leeggemaakt. Niet gerequired in actieve code (alleen `.bak` bestanden noemen het). **Veilig te verwijderen.**

### 2.4 `package.json`: dubbele SQLite drivers

Beide `better-sqlite3` (^12.6.2) **én** `sql.js` (^1.14.0) staan als dependency. `db.js:9` gebruikt **alleen** `sql.js`. CLAUDE.md zegt het tegenovergestelde:

> better-sqlite3 op disk. Memory zegt sql.js maar dat is verouderd

In werkelijkheid is **sql.js de actieve driver** (memory-resident, periodiek geserialiseerd via `forceSave()`). `better-sqlite3` is in node_modules wel aanwezig maar wordt nergens gerequired in actieve code. Dit is een fundamenteel feit dat verkeerd staat in CLAUDE.md en waarschijnlijk de oorzaak is van eerder verwarring rond DB-locks/integriteit.

Bijwerkingen:
- DB van 108MB volledig in geheugen gehouden + periodieke export (verklaart 651MB RSS bij idle)
- `sqlite3 -readonly` CLI commando's lopen tegen de **disk-versie** aan, die alleen ververst na `forceSave()` (elke 120s of bij signal)
- WAL-modus wordt niet gebruikt; `db.js:131` zet `PRAGMA foreign_keys = ON` maar geen WAL

### 2.5 `package.json` versie staat op 10.7.0

Werkelijke versie volgens git: 10.18.53. Volgens `lib/state.js`: 10.16.0. Volgens server health endpoint live: 10.16.0. Drie verschillende waarheden voor één getal.

### 2.6 Backups-pre-dedup directory

`/opt/t4c/backend/backups-pre-dedup/` bevat duplicaat-routes met namen zoals `routes__market.js.bak-pre-s4`. Deze bestanden hebben actieve `require(...)` statements en oude paden, maar vallen buiten de actieve `require`-graph (geen enkele `require()` verwijst naar deze directory). **Veilig te archiveren/verwijderen** (66KB).

### 2.7 Inconsistente endpoints voor inspecties

- `routes/inspectie.js:97` — `GET /api/inspecties` (auth, geen role-check)
- `routes/scanner.js:155` — `POST /api/inspecties` (auth)

Plus `inspectie.js:1` zegt "biedingen" in de file-comment, maar `routes/veilingen.js` heeft óók biedingen-routes. Twee modellen door elkaar:
- `inspectie.js`: `/api/biedingen/:kenteken`, `/api/biedingen`, `/api/bod`, `/api/bod/:id/status` (lossere gebruiks-context)
- `veilingen.js:242`: `/api/admin/biedingen` (admin overview)

Niet conflict op route-niveau (verschillende paden), wel conceptueel rommelig.

## 7. Security observations

### 7.1 Geen secrets gelekt in repo (✓)

`.env` staat in beide `/opt/t4c/.env` (mostly empty) en `/opt/t4c/backend/.env` (gevuld). Geen API keys in git-tracked files (alleen in env-files, niet committed).

### 7.2 JWT-secret rotation pad fragiel

JWT_SECRET wordt random gezet op eerste boot, opgeslagen in `settings`-tabel. Als die rij verdwijnt of `'CHANGE_THIS_TO_RANDOM_STRING_t4c2025'` wordt, regenereert hij — alle tokens worden ongeldig. Geen migratie/rotate-procedure gedocumenteerd.

### 7.3 Auth optioneel op `/api/dealer/price`

Endpoint is publiek (express.json zonder authMiddleware). Pas in body wordt token optioneel gelezen via `verifyToken()` (die niet bestaat — zie 2.2). Iedereen kan dus zonder auth een pricing-call doen. Dat is GPT-budget waarvoor je betaalt. Gewenst gedrag of niet?

### 7.4 `app.use(cors())` — open CORS

Volledig open. Voor publieke verkoop-site OK, maar `/api/dealer/price` etc. zijn open voor cross-origin scripts.

### 7.5 Hardcoded JWT secret in `lib/auth.js`

Secret string staat hardcoded als fallback in regel 3. Wordt overschreven bij boot, maar tot de overschrijving plaatsvindt is hij geldig — race condition window van enkele seconden tussen module-load en `setSecret()` aanroep in `server.js:201`.
